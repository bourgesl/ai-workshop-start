# Web view attack workflows

Choose probes based on actual entry points and trust boundaries. These are hypotheses, not pre-existing findings. Use bounded synthetic inputs and stop once the failure is demonstrated.

| Surface | Attack workflow | Evidence to establish |
| --- | --- | --- |
| Skill content and metadata | Put harmless HTML/script markers, quotes, closing tags, event attributes, and unusual Unicode in names, descriptions, raw Markdown, copy paths, repository names, warnings, and errors. Scan and select/filter the result. | Untrusted text remains literal. For injection, demonstrate an app-origin marker or unexpected DOM change originating from scan data, with the real delivery path. Never use an external exfiltration endpoint. |
| Links and shared scans | Exercise encoded query delimiters, fragments, malformed escapes, duplicate or empty `repo` values, whitespace, trailing slashes, misleading GitHub hostnames, credentials in URLs, and non-HTTP schemes. Inspect repository, source, and copy links. | Only supported targets are accepted; generated links retain their intended destination and commit. An input error is clear and does not execute a scheme or select an unintended target. |
| Local filesystem boundary | In temporary fixture directories, probe relative/absolute paths, traversal, symlinks pointing to another synthetic directory, and malformed path strings. Check the implementation's intended filesystem access. | Local directory scanning is specified functionality, not automatically a vulnerability. Establish an actual boundary bypass using marker files, attacker reachability, and relevant host/origin conditions; never probe real credentials or private directories. |
| Server fetch boundary | Inspect URL parsing and redirects before trying alternate hosts or addresses. Where relevant, use a local controlled HTTP listener and recorded redirect responses. | Show whether attacker input can cause an unintended server request and whether credentials could cross a host boundary, using dummy tokens. A mocked request alone does not prove external reachability or a bypass in production. |
| API and origin handling | Exercise missing/invalid parameters, unexpected methods, route names, error responses, and cross-origin requests from a second controlled local origin. Inspect actual browser requests as well as response headers. | Separate “request can be sent” from “response can be read.” Reproduce any claimed cross-origin scan/read and state preconditions. Loopback binding alone does not establish the complete browser trust boundary. |
| Upstream data and failures | Replay malformed front matter, unexpected API shapes, missing/truncated tree data, paginated responses, rate limits, inaccessible repositories, and skill parsing failures. | Failures stay explicit; successful results survive partial account failure; failed scans are not presented as empty. No secrets or unnecessary internals leak in errors. Distinguish deliberately malformed transport data from attacker-controlled GitHub content. |
| Asynchronous state | Delay one recorded scan, submit a second, then finish them in reverse order. Switch account/repository results, select skills, and type filters while requests complete or fail. | Only the latest submission updates the page. Counts, details, warnings, links, loading/error state, and selected skill all belong to the same scan. |
| Bounded resource stress | Increase name/description/Markdown length, skill count, nesting, and repeated submissions in small measured increments. Use a local disposable instance, request/time budgets, and cleanup. | Record payload sizes, elapsed time, responsiveness, and recovery. Do not call ordinary large-account latency a security bug without a concrete availability impact and feasible attacker input. No unbounded fuzz loops or traffic against GitHub. |
| Interaction and layout | Try narrow screens, long unbroken text, empty results, no filter matches, repeated scans, keyboard selection, and focus changes. | Check spec behavior: literal raw Markdown, pinned links, preserved warnings, valid selection and counts, usable focus, and no horizontal overflow. Label non-security regressions accurately. |

For each confirmed finding, minimize the input and replay it twice from clean state. Capture an observed failing invariant and the working control. State whether evidence comes from the real scan pipeline, recorded upstream data, or browser interception, and disclose what remains unverified.
